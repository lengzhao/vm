# 持久化状态插件（E1）

`state/bbolt` 为可选嵌入式持久化后端，同时提供 `core.StateStore`、`core.SnapshotStore` 和 Start/Stop 生命周期。默认配置继续使用 `state/memory`；`state/mvcc` 也保留。它只存储合约状态，编译产物仍由独立 ContractStore 管理。

## 配置与生命周期

完整示例见 [`presets/persistent.yaml`](../presets/persistent.yaml)，与 D3 的 `batch/ordered` 及 `engine/batched` 组合。

```yaml
state:
  use: state/bbolt
  config:
    path: ./state.db
    lockTimeout: 1s
```

`path` 必填，父目录必须已存在。相对路径在构造时转为绝对路径；构造不创建文件、打开数据库或启动 goroutine。数据库文件新建权限为 0600，已存在文件保留现有权限。`lockTimeout` 默认 1 秒，显式配置必须为正的 Go duration。

assembly 在完整配置图构造和类型校验后调用 Start，按依赖顺序打开数据库；失败启动会回滚已启动实例。Stop 按逆序关闭。直接调用插件工厂或 PluginKit 构建时，使用者必须自行 Start(ctx)/Stop(ctx)。未启动、已关闭或故障实例拒绝 Begin/Commit/Validate，返回可用 `errors.Is` 判断的 `core.ErrStateUnavailable`。

数据库文件由一个实例独占，第二实例/进程会在锁超时后失败，不会共享写入或降级内存。Start 的文件锁等待以短周期检查 context；文件读取、fsync 和关闭是同步内核 I/O，不承诺硬实时抢占。Start 成功后重复调用无副作用；Stop 幂等，成功关闭后不能在原实例重新 Start，重开须构造新实例。Stop 同步取消全部未结束事务；它们不再接受读写，仍能 Rollback 清理及检查读写集合。

## 快照与提交

运行时复用 MVCC 的不可变内存代际和每键身份令牌。Begin 获取当时快照，读写、缺失、删除、盲写及 ABA 检测与 `state/mvcc` 一致。快照不长期持有 bbolt 读事务，避免写事务扩容 mmap 时被自己的旧读事务阻塞。内存代际、冲突令牌与活动事务不跨重启保留；新实例从已落盘值重建，旧实例事务已被取消，因而无需跨重启保留 tombstone 历史。

一次有写提交在同一提交锁内依次执行：

1. 验证读写键版本及 context，准备全部新内存映射。
2. 在一个 bbolt 写事务中写入全部修改；参数/键限制或取消错误在提交前回滚。
3. 同步提交数据库（不启用 NoSync），再一次性发布已准备好的内存代际。

磁盘提交成功后不再执行可能失败的发布步骤，也不因随后并发取消而返回取消错误，避免“实际已提交但报超时”。只读事务校验版本并结束，不执行磁盘写入。正常业务失败、OOG、DryRun 与失败跨合约调用仍由 Engine 丢弃整链事务，不写数据库。

文件格式为 schema v1，使用固定根/值 bucket；复合键按 8 字节大端地址长度、地址字节、字段字节编码，支持空地址/空字段、任意二进制字符串，不使用分隔符拼接。空值与缺失分别表示。bbolt 的编码键长度上限为 32768 字节（含 8 字节前缀和地址）；超限提交在落盘边界前失败并回滚全部写入，运行时 Object 字段另有自己的更小限制。

未知 schema、外来数据库布局、无效键编码或库能检测出的文件损坏会拒绝启动，不自动迁移、清空或回退内存。schema 校验不是数据来源认证，不能识别所有合法格式内的内容篡改。

## 提交结果不确定

`core.StateTransaction` 的通常保证是失败提交不发布任何键。持久化 I/O 在写入/同步边界报错时，无法可靠断言磁盘上是旧状态还是新状态，因此新增明确异常：

```go
if errors.Is(err, core.ErrStateCommitUncertain) {
    // 暂停相关业务；Stop 该实例，使用新实例重开并核对持久状态。
    // 不盲目重试，也不把 Rollback 当成撤销已落盘提交。
}
```

这类错误保留底层 cause，Engine 通过 `ExecutionError` 的 cause 继续传递；批量调度停止并返回整体错误。后端立即进入故障隔离状态、取消活动事务，新的 Begin/Commit/Validate 返回 `ErrStateUnavailable`（保留不确定 cause），旧事务读写返回取消错误。Rollback 只能清理本地快照，不能撤销可能已完成的磁盘提交。

**批量返回前缀只表示已确认完成的项目。结果不确定的当前项即使不在前缀中，也可能已落盘。** 必须重开数据库并按业务标识核对状态后再决定是否重试，不能仅按前缀长度自动续跑。E1 不提供请求幂等账本、提交收据或“恰好一次”业务承诺；事件也不会因潜在落盘而自动补发。

只有在提交边界前明确失败的参数、冲突、取消等路径，才保证无写发布且后端可继续使用。首次数据库创建失败可留下空的或已初始化文件，但不包含业务写入；修复故障后重新打开，不擅自删除文件。

## 恢复和适用范围

固定依赖 `go.etcd.io/bbolt v1.5.0`，依赖官方模块代理及 checksum DB 校验。成功提交的持久性依赖操作系统、文件系统和设备兑现同步语义；首次启动同步父目录以固定新文件目录项。测试包含子进程在提交后不调用 Stop 直接退出、未提交写入不出现，以及提交前/提交后报告故障的两种注入结果。它们不等于真实断电、坏盘、任意 torn-write 或硬件耐久认证。

当前方案恢复时加载全部值入内存，写提交仅复制受影响的不可变分片；全量状态仍有 O(状态键数) 的内存开销，单次复制随受影响分片大小增长。单文件/单实例，不提供分布式一致性、自动 schema 迁移、加密、磁盘配额或区块级原子性；一致备份/恢复及容量统计见 [运维指南](operations.md)。生产备份应使用数据库支持的一致备份机制，不能假定正在写入的文件可直接安全复制。

D3 的确定性并行前提继续适用：批次期间无外部状态写入、产物替换或可变输入，合约及可信插件满足确定性约束。持久化不替代交易授权、业务幂等或链级恢复协议。

实现依据：[bbolt 官方说明](https://github.com/etcd-io/bbolt/tree/v1.5.0)，另见 [状态事务](state_transactions.md) 与 [有序并行执行](parallel_execution.md)。


## E2 批次回执扩展

同一schema v1根下新增隔离的 batches-v1 与 pending-batch-v1 元数据，guest状态仍在原 values bucket。E2 会话把状态、连续回执及最后一项的标记删除原子提交。未完成标记跨重启阻止其它写入，普通入口返回 ErrBatchPending，需保存原请求并恢复；不自动遗弃批次。maxBatchReceiptMB 默认64（4–1024）可在重开时提高。启用后应持续使用支持回执约束的版本，旧E1程序不理解未完成标记，不支持降级写入。详见 [可恢复批次](recoverable_batches.md)。
