# D1 Docker 沙箱设计与实施计划

**Goal:** 同时隔离 Go 编译与合约执行，限制资源，并验证负例。

**Architecture:** 用户已确认 Docker 路线。保持 core.Compiler / Runner 契约；编译器可选 Docker 配置，新增 runner/docker。复用现有协议解析与事务编排，容器退出及清理成功后才能返回成功。构造不访问 daemon，执行时只使用不可变镜像 ID，不拉取镜像，不回退宿主。

**Tech Stack:** Go、Docker CLI、Linux namespace/cgroup、Docker 默认 seccomp。

## 设计

- 编译仅挂载单次构建源目录（只读）和产物目录（可写）；禁网、禁 CGO、固定镜像工具链和 Linux/宿主架构。实际工具链摘要与镜像身份加入缓存身份。
- 执行复制并验证二进制快照，仅挂载该快照；只读根文件系统、非 root、全部 capability 移除、no-new-privileges、私有 PID/IPC、CPU/内存/进程/tmpfs 限制、禁止网络。
- 先 create 再 attach/start，使用随机容器名；任何返回路径强制删除容器。清理失败作为执行失败，保证 Engine 不提交状态。取消清理使用独立有界 context。
- policy/artifact 显式支持 Linux 目标配置，与 Docker Runner 匹配；ProcessRunner 仍只接受本机目标。默认配置保持开发路径。
- Docker daemon、内核、镜像与 VM 宿主属于信任边界；不宣称容器可防御内核漏洞。D2 后端比较后置。

## 实施顺序

1. internal/sandbox：先验证非法/可变镜像、资源参数、取消和隔离参数；实现受限容器命令与清理。
2. internal/process：先测试可替换启动与清理失败，再提取启动接缝，复用协议、Gas、Host 与输出预算。
3. internal/compiler：先测试 Docker 工具链/构建隔离与缓存身份，再接入 Linux 构建和清单；插件暴露配置。
4. plugins/runner、plugins/policy、assembly：先测试图装配，再接入显式沙箱配置，不扩大 core 能力。
5. Docker 集成测试：真实编译、执行、文件/网络拒绝、OOM、PID 限制、超时/后代清理；Object、跨合约和回滚回归。
6. 更新 docs/sandbox_roadmap.md、docs/plugins.md、README、todo。依次执行全量普通测试、race、vet、diff 检查。

变更保留当前 dev 工作区供审阅，不自动提交或推送。


## 验收结果

以上 1–6 已完成。显式启用真实 Docker 的全量普通测试、全量 race、go vet 与 git diff --check 均通过；测试后无残留 vm-d1 容器。独立审查及增量复核无剩余明确 P1/P2。创建控制请求超时采用 fail-closed 并报告结果不确定、保留容器名供管理员恢复；不承诺 daemon 失联后的自动回收。详见 todo.md 第九批记录。
